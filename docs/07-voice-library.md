# 音色库

## 一、现在什么样

角色编辑器里塞了一整条流水线：上传音频/视频 → 截取片段 → 语音识别 → 参考文本
输入框 → 保存。这些和"这个角色用哪个声音"是两件事，却混在一个对话框里。

数据上，一个"音色"其实是**一对**东西：

| 字段 | 存在哪 | 含义 |
| --- | --- | --- |
| `voice` | 角色 | 参考音频 wav 的路径 |
| `ref_text` | 角色 | 这段音频的**逐字文本** |

两者必须对应——声音克隆就是拿"这段音频 + 它说的话"去推断音色。但现在它们分开存
在每个角色上，于是：

- 两个角色想用同一个声音，要各写一遍参考文本
- 改了文本只改一个角色，另一个还是旧的
- 换个音频忘了改文本，就悄悄对不上了

### 一个已经存在的 bug

`ref_text` **只有编辑器在读写，从来没有传给语音流水线**。

切换角色时面板发的是：

```js
client.updateSession({ instructions: ..., voice: character.voice });
```

流水线那边 `_apply_session_voice_override()` 收到后设 `self.ref_audio = 新路径`，
但 `self.ref_text` 保持启动时 `services.json` 里 `--qwen3_tts_ref_text` 那一条不变。

也就是说：**换角色只换了音频，文本没换，克隆的依据是错位的。**
`web/js/realtime.js` 的 `buildSessionUpdate()` 也只认 `voice` 和 `instructions`
两个字段，没有传文本的通道。

## 二、改成什么样

### 数据

新增 `config/voices.json`，音色成为独立实体：

```json
{
  "voices": {
    "v-xiaoshu": {
      "label": "小舒的声音",
      "file": "assets/voices/voice-ms4cu9tx.wav",
      "ref_text": "今天天气不错，我们出去走走吧。",
      "created": "2026-07-29"
    }
  }
}
```

角色只留一个引用：

```json
"voice_id": "v-xiaoling"
```

**兼容旧配置**：角色里如果只有 `voice` 和 `ref_text` 没有 `voice_id`，启动时按
文件路径归并成一个音色条目，自动补 `voice_id`。旧字段保留不删，这样万一要回退，
配置还是能用的。

### 界面

角色编辑器里只剩一行：

```text
声音   [下拉: 小玲的声音 / 林知的声音 / 默认(英文)]  [试听] [管理…]
```

「管理…」打开独立的**音色库**对话框，那条流水线整个搬进去：

```text
音色库
  ┌ 已有音色 ─────────────────────────┐
  │ 小玲的声音    5.0s   [试听] [改名] [删除] │
  │ 默认(英文)    5.0s   [试听]              │
  └───────────────────────────────────┘

  新建音色
    上传音频/视频  [选择文件]  起点[0] 时长[10]  [截取]
    参考文本       [                    ] [语音识别]
    名字           [                    ]
                                        [保存音色]
```

顺序就是实际要走的步骤，名字在最后填——建好再起名。

顺带说清楚一个用词：这里没有"训练"。整条流程不改动任何模型权重，做的是提取——
把参考音频过一遍 speech tokenizer 得到 `ref_code`，再抽一个说话人向量
`ref_spk_embedding`。所以它是秒级的，不是分钟级的。

## 三、参考文本这件事，先把事实摆清楚

为什么音频能跟着切、文本不能：**启动参数是我们传的，运行时切换走的却是 OpenAI
Realtime 协议**，而那个协议里只有 `voice` 一个字段——它当初想的是"从预设音色里挑
一个"，没有"参考音频的逐字稿"这个概念。所以不是我们漏传，是协议里没这个位置。

Qwen3-TTS 自己的界面把这条规则写得很直白：

- 参考文本输入框：`Required if not set use x-vector only`（不勾 xvec_only 时**必填**）
- xvec_only 复选框：`仅用说话人向量，**效果有限**，但**不用传入参考音频文本**`

## 四、怎么补上的

配对关系并没有丢，只是协议里带不过去——`config/voices.json` 两半都有，从 clip
路径就能查回文本。所以补丁只要在库决定完 `ref_audio` 之后补一句。

`services/voice/launcher.py` 代替 `-m speech_to_speech.s2s_pipeline` 启动：
import 包 → 把 `Qwen3TTSHandler._apply_session_voice_override` 包一层 → 调
`s2s_pipeline.main()`。

**先调原方法，再补文本。** 原方法负责全部判断——这个 voice 是不是合法音频路径、
是不是 `custom_voice` 分支要改走 speaker（那条会把 `ref_audio` 置空）。它拒绝了
这次切换，`ref_audio` 就没变，查表也查不出新东西，行为跟没打补丁一样。

启动那一句也归 launcher 管：它按 `--qwen3_tts_ref_audio` 查表，改写
`--qwen3_tts_ref_text` 的值。否则第一个说话的角色是唯一走不到上面那层的情况，而且
在音色库里改了文本，`services.json` 里那份复制品就成了旧的。查不到就不动那个参数
——回落到配置里的文本虽然对不上，总好过一点文本都不给（ICL 模式会直接报错）。

**为什么不做 `.pt` 音色包。** 原来打算把音色烘焙成 `VoiceClonePromptItem` 存盘，
后来发现没必要：`faster_qwen3_tts/model.py:47` 自己就按 `(音频, 文本)` 缓存编码
结果，第一次用编码一次，之后整个进程都命中。烘焙能省的就是这一次。实测
`var/logs/voice.log` 里 59 次 TTFA，10 秒级的每一次前面都紧跟着一行
`Warming up Qwen3TTSHandler`（启动预热，含 CUDA graph 捕获），**除预热外全部落在
0.32–0.78 秒**——而那些会话里确实切过角色，也就是说其中必有 cache miss，一个都没
超过 0.78 秒。为几百毫秒搭一套烘焙流程、找地方加载模型、再管音频或文本改动后的
缓存失效，不划算。

**同时关掉了 `--qwen3_tts_xvec_only`。** 它当初开着是因为文本对不上，宁可不要
文本。现在文本跟得上了，就该走质量最好的 ICL 模式。这两件事必须一起做：只关开关
不打补丁会更糟（文本对不上还硬用），只打补丁不关开关则毫无作用（xvec_only 完全
忽略文本，连缓存 key 都不同）。

> 这一段记的是当时的决定。后来又换回 xvec_only 了，原因和代价见
> [四点七](#四点七开关又拨回去了以及界面为此变成跟着模式走)。上面这句
> "两件事必须一起做"仍然成立，只是方向反过来。

**风险**：补丁依赖 `_apply_session_voice_override` 这个私有方法名。所以 launcher
在 import 之后先断言它存在，不在就直接 `SystemExit` 退出——静默失效会得到一个
"看起来哪都正常、但每个角色都在用错文本克隆"的服务，比起不来坏得多。

## 四点五、开了 ICL 之后冒出来的一个坑

切过去当天就听出来了：每句话前面多一个"光"字。

参考文本结尾是 `...还有你至真至纯的阳光,`，而音频在 10.000 秒被切断，**"光"字只念
了一半**。语音识别照样把它写成完整的"阳光"——它听见这个词开了头，没理由只报一半。
于是 ICL 拿到的信息是"参考念到了光"，音频却没念完，模型就在每句话开头替它念完。

xvec_only 时代不会有这个问题：文本根本不参与。

实测四种改法（同一段参考音频、同一句目标文本，用 Whisper 读回生成结果）：

| 参考文本 | 结果 |
| --- | --- |
| 识别出来的原样 | `光,今天天气不错,...` |
| 把逗号改成句号 | `光,今天天气不错,...` |
| 去掉最后一个词 | `今天天气不错,...` ✓ |
| 去掉最后一整句，音频不动 | **27 秒胡言乱语** |
| 去掉最后一整句，音频一起裁 | `今天天气不错,...` ✓ |

两个结论。**标点无关**——这是我先猜错的那个。真正要紧的是**文本和音频必须描述同
一段话**：文本比音频短一大截比原来的毛病糟得多，模型手上多出好几秒没人告诉它的
参考音频，直接崩掉。

Whisper 对中文返回的是**句级**分块不是词级（10 秒 4 块，按逗号切），所以能用的最小
单位是句。因此 `server/transcribe.py` 的做法是：末句如果一直响到音频结尾，就把它从
文本里去掉，**同时把音频裁到前一句的结束时间**，再补 0.25 秒静音。静音既是克隆本来
就想要的，也让这件事幂等——再识别一次，末句不再顶到结尾，就不会再裁。

小满那条实测：10.00 秒 → 8.45 秒，文本去掉 `,还有你至真至纯的阳光`，重新合成
`今天天气不错我们出去走走吧`，干净。

所以音色库每一行加了「重新识别」：重读片段、重写参考文本，必要时连音频一起裁。
整件事在服务端一次做完（`POST /api/voicepacks/retranscribe?id=`），而不是让前端
先调识别再调保存——片段可能在中途变短，两次调用之间失败就会留下文本和音频对不上
的音色，正是这个功能要修的那种毛病。角色身上那份参考文本的副本也一并更新。

## 四点六、launcher 里搭车的第二个补丁：识别别跑两遍

跟音色无关，但住在同一个文件里，所以记在这。

`whisper_stt_handler.py:120` 用 `pred_ids[0, 1]` 读「刚才说的是哪国话」，指望那个
位置是 Whisper 以前会输出的 `<|zh|>` 标签。这个版本的 transformers 在返回前把强制
解码前缀去掉了——实测 5 秒中文的输出张量形状是 `(1, 2)`，两个都是正文 token，一个
特殊符号都没有。于是那一读永远不是合法语言码，判断失败，handler 就**把整段音频重新
生成一遍**。日志里每轮都有的 `Whisper detected unsupported language: `（冒号后面
是空的）就是它。同一行在片段只有一个 token 时还会 `IndexError`，直接把那一轮的识别
搞崩。

重跑那次唯一的区别是把语言设成我们本来就钉死的 `zh`，所以出来的文本一模一样，纯粹
是白等。`install_single_pass_stt()` 在语言已经钉死的时候接管 `process`：生成一次、
解码、按钉死的那个语言码发出去。实测（large-v3-turbo，取中位数）：

| 语音长度 | 库原样 | 打补丁后 |
| --- | --- | --- |
| 1 秒 | 122 ms | 70 ms |
| 2 秒 | 122 ms | 63 ms |
| 4 秒 | 279 ms | 148 ms |

文本逐字相同，这是验收的关键——补丁重写了识别那一步，只有拿真模型跑真语音对比原
实现，才谈得上安全。

`--language auto` 的时候不接管：那种情况下「是哪国话」是个真问题，我们没有验证过
的修法，交回给原实现（哪怕它在这个 transformers 版本下也是坏的），比瞎猜一个强。
这条路本应用不上。

**为什么这个补丁失效只打印一行、不像上面那个直接退出**：它换来的是速度不是正确性。
库的形状变了就该绕过去接着跑，没道理为此不让人开机。

## 四点七、开关又拨回去了，以及界面为此变成跟着模式走

ICL 用了一阵之后暴露出一个当时没想到的代价：**轮次之间音色会飘**。同一个音色包，
说几句话，听起来不像同一个人。原因是 ICL 把参考音频当上文续写，而每一轮回复都是
一次全新的续写——没有任何机制保证两次续写落在同一个音色上。

排查过程里有两个假设是我提的，都被自己的实验推翻了，一并记下来免得以后再走一遍：

| 假设 | 做法 | 结果 |
| --- | --- | --- |
| 是采样太随机 | temperature 0.9 / 0.7 / 0.5 / 0.3 各合四遍 | 离散度 4.98 / 7.26 / 6.70 / 6.59，**没有下降趋势**，推翻 |
| 是一条回复分了几次合成 | `stream_batch_sentences` 1 改 2 | 日志显示每条回复本来就是一次合成（人设限了"不超过两句"），**改了等于没改**，推翻 |

真正有效的是换回 xvec_only。同一句话各合四遍，两个句子上都成立：

| 模式 | 句子一 | 句子二 | 平均 |
| --- | --- | --- | --- |
| ICL | 7.96 | 7.79 | 7.87 |
| xvec_only | 4.06 | 2.91 | **3.48** |

（离散度是四遍之间 MFCC 均值到中心的平均距离，绝对值没有意义，只能横向比。）

**取舍很清楚：拿相似度换一致性。** 官方给 xvec_only 的评价是"效果有限"，这个代价
是真的；但"每句话都像别人"比"一直像个八分像的人"更难听。想换回去就把
`services.json` 里 `--qwen3_tts_xvec_only` 那一行删掉，飘会一起回来。

`stream_batch_sentences` 也跟着回到 1。它当初是为了压 ICL 的逐句抖动才改成 2 的，
说话人向量固定下来之后批合成就没有存在理由了，改回 1 把首字延迟（TTFA 0.3–0.5 秒）
赚回来。**注意 xvec 固定的只是"谁在说"，不是"怎么说"**：语气、轻重、语速仍然是每
句各生成一次的。

### 界面为此改成跟着模式走

xvec_only 下参考文本不是"影响变小"，是**根本没送进去**。
`faster_qwen3_tts/model.py:429`：

```python
if xvec_only:
    prompt_items = self.model.create_voice_clone_prompt(
        ref_audio=str(ref_audio),
        ref_text="",              # 传进来的文本在这里被丢掉
        x_vector_only_mode=True,
    )
    ...
    ref_ids = [None] * len(input_ids)
```

于是音色库里"参考文本 + 自动识别"整整一步在当前模式下是空转，而列表里那句"没有
参考文本，克隆效果会打折"更是**假的**——不打折。让用户填一个不会被读的框，还为
此警告他，是比多一个框更糟的事。

所以面板读 `scripts/services.json` 判断当前模式，`GET /api/voicepacks` 带回
`clone_mode`，界面据此决定文本那一步出不出现。**没有把功能删掉**：数据、
launcher 补丁、`重新识别` 按钮全部留着，哪天把那一行删掉换回 ICL，界面自己就变
回来了。

读不出来的时候一律当 ICL 处理——那样最多是多显示一个用不到的框，反过来则会在真
正需要文本的模式下把它藏起来，而 ICL 缺文本是会直接报错的。

有一个已知的缺口：xvec 模式下新建的音色不会有参考文本，将来换回 ICL 时它们是缺
的。没有为此自动去跑一遍识别（要几十秒，为一个当前用不到的字段不值），列表在 ICL
模式下本来就会把缺文本的条目标出来，一条点一下`重新识别`就补上了。

## 五、验证

1. 建一个新音色：上传 → 截取 → 识别 → 起名 → 保存，`voices.json` 里出现条目
2. 两个角色选同一个音色，`characters.json` 里都是 `voice_id`，文本只有一份
3. 旧配置（只有 `voice` + `ref_text`）打开后自动归并，声音不变
4. 删除一个正在被角色使用的音色，要有提示而不是让角色指向空
5. 新建音色点「语音识别」，如果原片段是从中间切断的，时长会变短一点，文本也不再
   带那半个字——两者必须同时变
6. 切到一个非默认音色说一句，`var/logs/voice.log` 里出现
   `voice launcher: reference transcript now matches ...`，路径是新音色的 clip
7. 说几句话，`var/logs/voice.log` 里**不应该再有**
   `Whisper detected unsupported language:`——还有的话说明单次识别的补丁没装上
8. `GET /api/voicepacks` 返回里带 `clone_mode`，值和 `services.json` 里那一行
   对得上
9. 当前（xvec_only）模式下打开音色库：没有参考文本输入框、没有「语音识别」和
   「重新识别」按钮、列表里不再有「没有参考文本」的黄字
10. 把 `--qwen3_tts_xvec_only` 那一行删掉、重启面板，上面那些**全部自己回来**
    ——这一条是整个改动的意义所在，只藏不删
11. 故意把 `services.json` 改坏再打开音色库：文本那一步要照常出现（读不出来当
    ICL 处理）
